# DAY ZERO — Should agent infrastructure be the first technical theme?

**Question:** is "agent infrastructure" the right first theme for DAY ZERO, or is it the
obvious answer that everyone building an AI sourcing tool will pick?

The mandate says not to force this conclusion. So the theme is compared against four
alternatives on criteria that matter for *sourcing*, not for investing.

## 2. Problem → current solution → failure mode → emerging projects → possible formation

All projects named below were verified via the GitHub API on 2026-08-22. Naming a project
here is an observation about the artifact, not a claim about the people's intentions.

### 2.1 Agent isolation and execution boundaries
- **Problem:** an agent that can run code can run *any* code, on a machine that also holds
  credentials and source.
- **Current solution:** Docker; a whole-VM; or nothing.
- **Failure mode:** containers are a poor security boundary against code an LLM wrote;
  full VMs are too slow to spawn per task; "nothing" is common.
- **Emerging projects:** `deeplethe/forkd` (KVM microVM CoW fork, Rust, 2026-05-11);
  `boxlite-ai/boxlite` (embeddable micro-VM, Rust, 2025-12-07); `earendil-works/gondolin`
  (Linux microVM + TS control plane); `opensandbox-group/OpenSandbox`;
  `eugene1g/agent-safehouse` (least-privilege FS scoping); `h5i-dev/h5i` (per-agent
  disposable sandbox over a Git-backed forum); `FootprintAI/Containarium` (eBPF egress
  policy + GPU passthrough).
- **Formation shape:** small orgs, .dev/.ai domains, 1–3 identified maintainers.
- **Array fit:** direct — Array's own AI coworker runs in "its own filesystem sandbox with
  isolated execution."

### 2.2 Agent identity, authority, and budget
- **Problem:** ~100 non-human identities per human; agents hold tokens and spend money.
- **Current solution:** service accounts and static API keys.
- **Failure mode:** no per-action authorization, no budget enforcement *before* execution,
  no audit trail of what an agent spent and why.
- **Emerging projects:** `thunder-id/thunderid` (identity stack for humans/agents/machines
  — **flagged NC-6, contributor pattern suggests an established team**);
  `spinningfactory/kloak` (zero-trust for agent runtimes);
  `microsoft/agent-governance-toolkit` (incumbent, context only).
- **Already solved commercially:** **Sapiom is Array's own answer here** — budgets and
  permissions enforced before execution, full audit trail, cost per step.
- **Array fit:** direct, and *partially occupied by the portfolio*. That is a reason to be
  careful, not a reason to avoid the area.

### 2.3 Agent economics / cost accounting
- **Problem:** nobody knows what agent work costs per unit of accepted output.
- **Current solution:** provider dashboards; token counting.
- **Failure mode:** tokens are an input metric. Array's own post: measure **accepted work
  units**, not tokens.
- **Emerging projects:** `getagentseal/codeburn` (cost across 37 tools, org created
  2026-04-18, founder-identified); `mikehasa/agentacct` (per-task work-step accounting,
  created 2026-07-24, solo); `vivekchand/clawmetry` (governance + live cost across 20+
  runtimes); `headroomlabs-ai/headroom` and `rtk-ai/rtk` (reduce the cost rather than
  measure it).
- **Formation shape:** very early; several are single-maintainer with <6 months of history.
- **Array fit:** **direct and the least crowded relative to Array's stated interest.**
  Theme 3 plus the entire July 2026 AWU argument.

### 2.4 Context and memory
- **Problem:** loops need durable state; context windows are finite and expensive.
- **Current solution:** RAG, vector DBs, ad-hoc summarization.
- **Failure mode:** retrieval quality is unmeasured; every framework ships its own memory.
- **Emerging projects:** an enormous field — `vectorize-io/hindsight`, `MemoriLabs/Memori`,
  `MemTensor/MemOS`, `Gentleman-Programming/engram`, `gastownhall/beads`,
  `rohitg00/agentmemory`, `MemPalace/mempalace`, and many more.
- **Array fit:** Theme 7, direct.
- **Sourcing verdict: this is the most crowded and lowest-signal-density area in the whole
  landscape.** Star counts here are enormous and differentiation is nearly invisible from
  outside. It is where NC-2 (thin wrapper as infrastructure) is most likely to fool us.

### 2.5 Agent observability and reversibility
- **Problem:** you cannot debug or bound what you cannot see.
- **Current solution:** LLM tracing tools built for a single-call world.
- **Failure mode:** traces show prompts, not system effects — the exact critique in
  *Agents broke the security stack* ("moves data through syscalls").
- **Emerging projects:** `eunomia-bpf/agentsight` (**eBPF, system-level, with
  arXiv:2508.02736**); `shepherd-agents/shepherd` (reversible Git-like execution trace,
  fork/replay/revert); `Brain0-ai/brain0` (commit↔prompt provenance, signed attestations);
  `secureagentics/Adrian`; `FailproofAI/failproofai` (policy enforcement).
- **Array fit:** Themes 2 and 3, plus the security thesis.

### 2.6 Inference efficiency
- **Problem:** serving cost dominates agent economics.
- **Emerging projects:** `ovg-project/kvcached`, `uccl-project/uccl` (Berkeley; two arXiv
  papers), `smg-project/smg`, `pegainfer-project/pegainfer`, `brontoguana/krasis`,
  `youssofal/MTPLX`.
- **Array fit:** Theme 4 (Edge Intelligence: Inference, Optimization, Efficiency).
- **Sourcing verdict:** the highest *technical depth* density of any area, and the hardest
  to verify without GPUs (see `reproduction_lab.md` §2). Also the area where academic labs
  dominate and formation is rarest (NC-7).

## 4. Recommendation

**Yes — agent infrastructure should be the first theme, but narrowed.**

The unqualified phrase "agent infrastructure" covers both the most crowded area in open
source (memory/context) and the least crowded (economics). Adopting it wholesale is the
generic answer, and it would drown the system in NC-2 wrappers.

**The recommended first theme is: the agent execution and accountability layer —
isolation boundaries, identity and authority, budget enforcement, and cost-per-accepted-
work-unit measurement.**

Why this narrowing is defensible:

1. It is the intersection of Array's two most recent and most specific pieces of writing
   (the security post's four wanted categories, and the AWU/LoopOps argument).
2. It is the area where Array has *operating* evidence rather than only thesis evidence —
   they run an internal agent with a sandbox, a heartbeat, and on-demand tools, and that
   stack generated the Sapiom investment.
3. Its claims are measurable on an 8 GB M1: token counts, latency, and policy enforcement
   are all laptop-verifiable, unlike KV-cache quantization.
4. It has the lowest artifact density of the agent sub-areas, which means the ratio of
   real construction to attention is *better*, not worse.
5. **Sapiom is a genuine caution, not a disqualifier.** Array already owns a strong
   position in agent budgets and permissions. That makes the area a place to look for
   *adjacent* layers — execution isolation, provenance, cost attribution — and it makes
   any lead here require an explicit "how is this different from Sapiom?" question.

**Second theme: agent-era security**, driven directly off Array's four published wanted
categories.
**Backtest theme: data infrastructure**, because Eventual/Daft provides the cleanest
recoverable pre-financing evidence trail in the portfolio.

## 5. The counter-argument, stated fairly

Agent infrastructure in 2026 is where every AI-native sourcing tool will point. Picking it
is not differentiating. What is differentiating is (a) the narrowing above, (b) refusing
to treat star counts as signal in the most star-inflated category on GitHub, and (c) the
willingness to run the compression and memory-benchmark claims rather than repeat them.
If DAY ZERO's output in this theme looks like a list of the top-starred agent repos, the
theme choice was wrong regardless of the reasoning.
